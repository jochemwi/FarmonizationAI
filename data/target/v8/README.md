# v8 target data structure contract

v8 is a target contract for daily crop-model inputs. Repeated source samples and events are consolidated upstream before registration. It splits the three v7 observation tables into a summary table and a timeseries table: `Soil_layer_observations`, `Crop_observations`, and `Other_observations` each have `*_summary` and `*_timeseries` variants.

Rows with an explicit `date_of_measurement` belong in the corresponding `*_timeseries` table. The date is required there. Rows without an explicit observation date belong in the corresponding `*_summary` table; summary tables do not expose `date_of_measurement`, `BBCH_time_of_measurement`, or `event_time_of_measurement`. Here, summary means an observation without an explicit measurement date. All observation value columns are available in both variants so routing a row never discards its measurements. Only `date_of_measurement` controls routing: crop dates such as `anthesis_date`, `harvest_date`, `emergence_date`, `silking_date`, and the other growth-stage date fields are phenological measurements and do not establish the observation date. For example, a row containing `anthesis_date=2026-06-01` and no `date_of_measurement` belongs in `Crop_observations_summary`.

`Crop_observations_summary` uses `plot_season_id + group_plot_season_ids` as its logical key. `Soil_layer_observations_summary` uses `plot_season_id + me_soil_layer_top_depth + me_soil_layer_bot_depth + group_plot_season_ids`. Different canonical group lists therefore distinguish summary rows even when their other key fields match. The timeseries keys retain `date_of_measurement` and their existing plot-season and layer grain.

The removed observation timing columns have no separate role in this crop-model contract. A source BBCH or event-time label does not create a measurement date or a timeseries row. An observed `growth_stage_BBCH` remains a measurement value and is available in both variants. Do not infer a calendar date from it or restore the removed timing columns.

Use `fill_api.py --check-templates` to verify template headers and `fill_api.py --validate-package <directory> --complete` to validate a complete v8 package. A partial package is reported as `Package is valid for the supplied partial tables`; it is still rejected when a supplied table needs missing cross-table context.

Validation is deliberately split into two deterministic layers. `database_validation.py` checks CSV/API structure, field presence, scalar types, date and number syntax, code vocabularies, and duplicate logical keys. `domain_validation.py` checks agronomic meaning, including paired and ordered soil boundaries, event time context, and single-season crop observation dates against linked planting and harvest events. `fill_api.py` is the single entry point that runs both layers and adds package-level foreign-key checks. The crop-date rule runs during package validation because it needs the linked plot-season, treatment, genotype, planting, and harvest rows.

The single-season crop whitelist is explicit in `domain_validation.py` and contains all current `Repro_type=Annual` codes from `scheme/Crop_codes.csv`. A regression test keeps the whitelist synchronized with that contract source. For a single-season crop, a dated crop observation requires concrete linked planting and harvest dates and must fall between them. Missing dates are errors; the API does not infer them.

For mixed observation input, call `route_observation_rows` with the v7 base table name. It returns the matching summary and timeseries lists and routes solely by whether `date_of_measurement` contains a non-blank value. It removes a blank date field from summary rows; validate and write each returned list with its target table name. API row objects must include every `required` and `required_nullable` header; optional headers may be omitted.

Missing values are empty CSV cells. API callers may supply an empty string, Python `None`, or JSON `null`; the API normalizes these to an empty string and writes an empty CSV cell. Literal text such as `"None"` is not a missing-value marker. Fields marked `required_nullable` must remain present in the CSV/API row schema but may be blank; `required` fields must have a value. In v8 this includes the initial-conditions measurement date and optional treatment-component links; blank nullable foreign keys are accepted by package validation. Date fields use ISO `YYYY-MM-DD`, which is also enforced by the API. Every date field declares `Unit_or_type=date` and `Data_type=date`, and its description states the `YYYY-MM-DD` format.

Soil-layer boundaries are paired: `me_soil_layer_top_depth` and `me_soil_layer_bot_depth` must either both have values or both be blank, and the upper boundary cannot be deeper than the lower boundary. Overlapping rows are allowed because real sampling intervals can overlap. For event tables, each event phase must provide at least one of its date, phenology-time, or event-time fields; a row with all three blank is rejected.

`group_plot_season_ids` is a collection-valued foreign key declared in both `variables.csv` (`FK_Reference`) and `table.csv` (`Foreign_keys -> Plot_seasons.plot_season_id`). It is required on every observation or layer row and is stored as a semicolon-separated list of one or more existing `Plot_seasons.plot_season_id` values. For rows that also have `plot_season_id`, the primary `plot_season_id` must be included in the group list. A single plot-season is written as one ID; broader observations may list several IDs. The API trims each ID, rejects empty or repeated IDs, writes the canonical lexicographically sorted list, and checks every member against the parent table during package validation. This uses Python enforcement because one CSV cell represents several parent-key references; it is still a foreign-key contract rather than a free-text field.

Timeseries observation tables use one row per plot-season and calendar date; soil-layer and other observation timeseries also include the layer-boundary pair in that grain. Consolidate repeated same-day numeric state observations to daily means upstream before registration. Separate original samples are intentionally not retained in this target contract. Date, code, and text values must retain their meanings when resolving the daily record. The API rejects duplicate logical keys and does not calculate daily means.

For event tables with composite keys, the key is intentional. Consolidate repeated daily applications upstream: additive quantities such as irrigation depth and applied material amounts use daily sums; numeric state or rate measurements use daily means where applicable. Methods, materials, dates, and codes must retain their meanings in the consolidated record. Two rows with the same treatment and event-time key are rejected as duplicate logical events. The API does not calculate daily means or sums and does not merge source events.

`variables.csv` carries both the semantic `Variable_name` and the physical `Target_column`. For rows with an `ICASA_var_uid`, `Variable_name` is the original ICASA `Variable_Name` from `icasa_variable.csv` after trimming source-file surrounding whitespace; this preserves the source spelling, including historical spellings. Target-only context, grouping, provenance, and timing fields have no ICASA UID and use explicit v8 names. `Target_column` is different only when the same conceptual variable occurs more than once in one table, such as the two canopy-length definitions; it prevents hidden column-name rules from changing CSV/API identity. v8 table names remain the target contract names, while the original ICASA logical sheet and variable identity are carried by `ICASA_var_uid` and `icasa_variable.csv`; summary/timeseries splitting does not rename an ICASA variable. At import, `fill_api.py` compares table primary keys and foreign keys with `variables.csv`, verifies every ICASA UID and source variable spelling, checks every foreign-key target against a declared parent primary key, and requires every code field to have a field-scoped `CODE_SOURCES` vocabulary mapping. In source files that carry `Variable_name`, rows with no owning variable are never treated as wildcards; dedicated shared vocabularies remain explicitly mapped by field and code display. Date fields use ISO syntax, and default numeric bounds apply only to `required` and `required_nullable` numeric fields.

This code-list design follows the supplied ICASA workbooks: their Dictionary records pair each `var_name` with a `Code_Query` and a strict validation list (for example, `irrig_applied` uses `IRRIG` and a logical list, while `harvest_operat_component` uses `HACOM` and a harvest-component list). v8 keeps that field-plus-code-display identity in `CODE_SOURCES`; a shared source file is allowed only when it is the same semantic vocabulary for the mapped fields.

The v8 target contract preserves the original ICASA spellings for all variables carrying an ICASA UID, including `realtive_humidity_avg`, `physiologic_maturity_dat`, and `pod_over-mature_stage`. New v8-only fields are identified by a blank `ICASA_var_uid` rather than by silently renaming an ICASA variable.

`Planting_events` and `Mulch_events` are treatment-level event records referenced from `Treatments`: one planting treatment record per `planting_treatment_id` and one mulch interval per `mulch_treatment_id`. Their planting, application, and removal dates are single treatment-level milestones by design; duplicate treatment rows are rejected. This is intentional in the current variable design; a future requirement for multiple mulch intervals per treatment would need a separate event identifier and a schema change.
